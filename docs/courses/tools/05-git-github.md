# 第 5 回　Git と GitHub：変更の記録と共有

!!! abstract "この回の道筋"
    プログラムや入力ファイルを書き直していると、「先週動いていた版」に戻りたくなることがあります。
    Git は、ファイルの変更の記録をとり、いつでも前の版に戻れるようにする道具です。GitHub は、その記録をネットワーク上に置いて共有する場所です。
    この回では、Git の基本の流れ（コミット、ブランチ、リモートとの push と pull）と、リポジトリに入れてはいけないものを学びます。

## 1. なぜ変更を記録するのか

解析のプログラムを直すたびに、`analysis.py`、`analysis_v2.py`、`analysis_v2_final.py` のように写しを増やしていくと、どれが最新で、どこを変えたのかが分からなくなります。
**バージョン管理**（version control）は、この問題を解く仕組みです。
ファイルは 1 つのまま、変更のたびに「いつ、誰が、何を、なぜ変えたか」の記録を残し、必要なら前の状態に戻せます。

**Git** は、最も広く使われているバージョン管理の道具です [Chacon 2014]。
研究でプログラムを書くときにバージョン管理を使うことは、広く勧められています [Wilson 2014; Blischak 2016]。
Git は自分一人の作業の記録にも役立ち、共同研究者とのファイルの共有にも使えます。

**ここまでで分かったこと**：Git は、ファイルの写しを増やさずに、変更の記録を残して前の版に戻れるようにする道具です。

## 2. リポジトリとコミット

Git で記録をとるディレクトリを**リポジトリ**（repository）と呼びます。
ふつうのディレクトリをリポジトリにするには、その中で `git init` を実行します。

```console
$ cd ~/project/analysis
$ git init
```

すると、隠しディレクトリ `.git` が作られ、記録はすべてこの中に保存されます。

初めて Git を使うときは、記録に残す名前とメールアドレスを登録します。

```console
$ git config --global user.name "Taro Yamada"
$ git config --global user.email "taro@example.com"
```

この名前とメールアドレスは、すべての記録に書き込まれ、GitHub に公開すると誰でも読めるようになります。
メールアドレスを公開したくないときは、GitHub が用意している公開用のアドレス（GitHub の設定画面の「Emails」で確かめられます）を使います。

変更の記録の 1 回分を**コミット**（commit）と呼びます。
コミットは、次の 2 段階で作ります。

1. `git add` で、記録に入れるファイルを選びます。選ばれた変更は**ステージングエリア**（staging area、次のコミットに入れるものを置いておく場所）に入ります。
2. `git commit` で、ステージングエリアの内容を 1 つのコミットとして記録します。`-m` の後に、変更の説明（**コミットメッセージ**）を書きます。

```console
$ git add analysis.py
$ git commit -m "エネルギーを kcal/mol で表示する"
```

2 段階になっているのは、いくつかのファイルを同時に直していても、その中から関係のある変更だけを選んで 1 つのコミットにできるようにするためです。
1 つのコミットには 1 つのまとまった変更を入れ、メッセージには「何を、なぜ」変えたかを書きます。
後で記録を読み返すとき、メッセージだけで変更の中身が分かるからです。

作業中は、`git status` で今の状態を確かめます。
`git status` は、前のコミットから変わったファイル、ステージングエリアに入っているファイル、Git がまだ記録の対象にしていないファイルを分けて表示します。

**ここまでで分かったこと**：リポジトリの中で、`git add` で変更を選び、`git commit` で記録します。

## 3. 記録を見る・前の版に戻る

これまでのコミットの一覧は `git log` で表示します。
各コミットには、`3f9a2c1...` のような長い英数字の番号（**コミット ID**）が付いていて、これでコミットを指定します。
`git log --oneline` とすると、1 つのコミットを 1 行で短く表示します。

変更の中身は `git diff` で見ます。

```console
$ git diff                  # まだ add していない変更
$ git diff --staged         # add して、まだ commit していない変更
$ git diff 3f9a2c1 HEAD     # コミット 3f9a2c1 から最新のコミットまでの変更
```

`HEAD` は、今の作業の元になっているコミット（ふつうは、今いるブランチの最新のコミット）を表す名前です。

ファイルを前の状態に戻すには `git restore` を使います。

```console
$ git restore analysis.py                  # まだ add していない変更を捨てる
$ git restore --source=3f9a2c1 analysis.py # コミット 3f9a2c1 のときの中身に戻す
```

2 つ目の命令で戻るのは、手元のファイルの中身だけです。
戻した状態を記録に残すには、ふつうの変更と同じく `git add` と `git commit` をします。

!!! warning "コミットしていない変更は戻せません"
    上の 2 つの命令は、どちらも手元のファイルを上書きします。
    上書きで消えた変更のうち、add もコミットもしていないものは、どこにも記録されていないので取り戻せません。
    Git が守れるのは、コミットした内容だけです。こまめにコミットしておくと、安全に試行錯誤ができます。

**ここまでで分かったこと**：`git log` と `git diff` で記録を見て、`git restore` で前の版に戻せます。

## 4. ブランチ

新しい解析の方法を試したいが、今動いているプログラムは壊したくない、ということがよくあります。
このとき使うのが**ブランチ**（branch）です。
ブランチは、コミットの記録の枝分かれで、1 つのリポジトリの中に、互いに影響しない複数の作業の流れを持てます。

リポジトリを作ると、最初のブランチが 1 本できます。
その名前は、Git の版と設定によって `main` か `master` になります。
以下では `main` とします。
`master` になったときは、`git branch -m main` で名前を `main` に変えられます。
すべての新しいリポジトリで `main` にするには、`git config --global init.defaultBranch main` と設定しておきます。

```console
$ git switch -c new-fit     # new-fit というブランチを作って移る
（ここでファイルを直し、add と commit をくり返す）
$ git switch main           # main に戻る（new-fit での変更は見えなくなる）
$ git merge new-fit         # new-fit での変更を main に取り込む
```

`git switch` でブランチを移ると、ディレクトリの中のファイルが、そのブランチの最新のコミットの状態に置き換わります。
試した方法がうまくいかなければ、`main` に取り込まずにブランチを捨てればよいだけです。

2 本のブランチで同じファイルの同じ場所を別々に変えていると、`git merge` はどちらを残すか決められません。
これを**衝突**（conflict）と呼びます。
このとき Git は、ファイルの中に両方の版を `<<<<<<<`、`=======`、`>>>>>>>` の印で区切って書き込み、作業を止めます。
ファイルを開いて正しい形に直し、印を消してから、`git add` と `git commit` で取り込みを終えます。

**ここまでで分かったこと**：ブランチを使うと、今の版を壊さずに別の作業を試し、うまくいったら `git merge` で取り込めます。

## 5. リモートと GitHub：push と pull

ここまでの記録は、すべて手元の計算機の `.git` の中にあります。
ほかの計算機（手元のパソコンと計算機クラスタなど）や、ほかの人と記録を共有するには、ネットワーク上にもう 1 つリポジトリを置きます。
これを**リモート**（remote）リポジトリと呼びます。

**GitHub** は、リモートリポジトリを置くための Web のサービスです。
GitHub でリポジトリを作るときに、誰でも見られる**公開**（public）か、許可した人だけが見られる**非公開**（private）かを選びます。
研究室の中だけで使うものは、非公開にします。

手元のリポジトリを GitHub のリポジトリとつなぐには、次のようにします。
URL は、GitHub のリポジトリのページに表示されるものを使います（下は例です）。

```console
$ git remote add origin git@github.com:taro/analysis.git
$ git push -u origin main
```

`origin` は、つないだリモートに付けた名前で、慣習でこの名前を使います。
`git push` は、手元のコミットをリモートに送る命令です。
`-u` は、手元の `main` とリモートの `main` を組にする指定で、2 回目からは `git push` だけで送れます。

反対に、すでに GitHub にあるリポジトリを手元に写すには `git clone` を使い、リモートの新しいコミットを手元に取り込むには `git pull` を使います。

```console
$ git clone git@github.com:taro/analysis.git   # リポジトリを丸ごと写す（最初の 1 回）
$ git pull                                     # リモートの新しいコミットを取り込む
```

複数の場所で作業するときは、「作業を始める前に `git pull`、終わったらコミットして `git push`」を習慣にします。
`git pull` は、リモートの変更を手元のブランチに取り込む操作なので、4 節と同じ衝突が起こることがあります。
直し方も 4 節と同じです。

GitHub との通信には、第 1 回の 8 節で学んだ ssh の鍵が使えます。
公開鍵を GitHub の設定画面に登録すると、上の例のような `git@github.com:...` の形の URL で push と pull ができます。
`https://` で始まる URL を使うこともできますが、そのときは GitHub のパスワードではなく、GitHub の設定画面で作る**トークン**（token、パスワードの代わりに使う長い文字列）を使います。

**ここまでで分かったこと**：GitHub にリモートリポジトリを置き、`git push` で送り、`git pull` で取り込みます。

## 6. .gitignore と、入れてはいけないもの

リポジトリに入れるのは、人が手で書いたファイルが中心です。
解析のプログラム、計算の入力ファイル、ジョブスクリプト、論文の原稿などがそれに当たります。

反対に、次のものはリポジトリに入れません。

- **大きな計算データ**：出力ファイル、波動関数のファイル、積分のファイル、軌道の画像など。出力ファイルや画像のような大きなファイルは、変えるたびに丸ごと記録に残るので、リポジトリがすぐに重くなります [Blischak 2016]。大きなデータや結果のファイルはバージョン管理に入れない、というのが一般的な勧めです [Wilson 2017]。
- **プログラムを実行し直せば作れるもの**：図の PNG、Python が作る `__pycache__` など。
- **秘密の情報**：ssh の秘密鍵、トークン、パスワードを書いたファイル。
- **個人の情報や、公開してよいか分からないデータ**：共同研究先から預かったデータ、公表前の実験データ、他人のメールアドレスなど。

Git に無視させたいファイルは、リポジトリの一番上に置く **.gitignore** というファイルに書きます。
1 行に 1 つ、ファイルの名前か、`*` を使った名前の型を書きます。

```text
# 計算の出力と一時ファイル
*.out
*.log
*.chk
*.gbw
scratch/

# 実行し直せば作れるもの
__pycache__/
*.png

# 秘密の情報
.env
id_ed25519
```

`#` で始まる行は注釈です。
`scratch/` のように最後に `/` を付けると、その名前のディレクトリの中身すべてを無視します。
.gitignore に書いたファイルは、`git status` に表示されず、`git add .`（今のディレクトリのすべてを選ぶ）でも選ばれません。
ただし、.gitignore はすでにコミットしたファイルには効きません。

!!! warning "一度コミットしたものは、記録に残ります"
    間違えてコミットしたファイルを次のコミットで消しても、前のコミットの中にはそのファイルが残っています。
    そのコミットを GitHub に push していれば、リポジトリを見られる人は誰でも、記録をさかのぼって読めます。
    秘密鍵やトークンを push してしまったときは、記録から消す前に、まずその鍵やトークンを使えなくして（GitHub や施設の設定で削除して）、新しいものを作ってください。
    コミットする前に `git status` と `git diff --staged` で、入れるものを確かめる習慣が、いちばんの予防です。

**ここまでで分かったこと**：リポジトリには手で書いたファイルだけを入れ、計算データや秘密の情報は .gitignore で除きます。一度 push したものは取り消せないと考えます。

## まとめ

- Git は、ファイルの変更をコミットとして記録し、いつでも前の版に戻れるようにする道具です。
- `git add` で変更を選び、`git commit` で記録し、`git log`・`git diff` で記録を見ます。
- ブランチで別の作業を試し、うまくいったら `git merge` で取り込みます。
- GitHub のリモートリポジトリに `git push` で送り、`git pull` で取り込みます。
- 大きな計算データ、秘密の情報、個人の情報はリポジトリに入れず、.gitignore で除きます。
